2.3 Business Context

The Dealer Details Review screen must never be blank. When a dealer signs a contract with

Tekion, their basic details — name, address, phone, website URL — are captured in Salesforce

as part of that contract. Salesforce is already integrated with TOC (Tekion Operating Cloud) —

the internal operational system through which the dealer's instance is provisioned and

configured — and syncs dealer data into TOC as part of the contracting and provisioning

pipeline. TAO connects to TOC only; TAO does not read from Salesforce directly. TOC is

therefore the single source of dealer truth for TAO.

Layer 1 — Internal data sync (baseline, always present): At provisioning stage, TAO reads

dealer details from TOC. TAO writes this record into the TAO dealer record. When the Dealer

Admin opens the Dealer Details Review screen, all fields are already populated from this

baseline. This applies to every dealer — large, small, with or without a website. The no-blank-

field guarantee comes from this layer.

Data flow: Salesforce → TOC ← TAO  — Salesforce pushes dealer data into TOC; TAO reads

from TOC.

Layer 2 — Website scraping (enrichment, additive): For dealers that have a public website,

TAO also scrapes that website and compares what it finds against the merged internal record

already on file. Contract/TOC data may be from months ago and may have a slightly different

address or missing website URL. The website scrape surfaces these differences without

discarding what Tekion already knows.

The Dealer Admin experience — before/after comparison view:

All fields pre-populated from the merged internal record (Salesforce + TOC); labelled “From

your records on file”

Where the website found something different or new, a side-by-side comparison: “On file: 123

Main St | Found on website: 123 Main Street, Suite 100 | Use website version?”

Where the website found the same value → a quiet checkmark (no action needed)

Where the website found nothing new → on-file value shown alone, no comparison row

The Dealer Admin confirms the final state once. They are not re-typing anything — they are

reviewing and accepting/rejecting diffs.

Small dealers with no website: Contract data fills the screen completely. No comparison rows

appear because there is nothing to compare. The experience is: fully prefilled form from

contract, Dealer Admin reviews and confirms.

dealer-admin-corrected website URL: If the website URL in the contract is wrong, missing, or

the Dealer Admin wants to try a different page, the Dealer Details Review screen offers a “Try a

different website” option that allows a fresh scrape. The same URL validation rules apply to any

dealer-admin-provided URL before its scraped data is shown.

§12. Technical Approach

Standard feature mode — engineering-review format. AI capability mapping

not required.

Architecture — Two-Layer Model

This feature has two independent layers that compose on the Dealer Details Review screen.

Layer 1 — Internal Data Sync (baseline, always runs)

Data flow:  Salesforce → TOC → TAO

1. TOC Sync Service — At IM provisioning stage, reads the dealer record from TOC. TAO does

not connect to Salesforce directly — TOC is the single API call.

2. TAO Dealer Record — Stores the TOC-sourced dealer record. Dealer Admin screen reads

from here. Always populated before the Dealer Admin journey begins.

Layer 2 — Website Scraping + Comparison (enrichment, additive)

3. Scrape Trigger — Resolves the dealer website URL from the TAO dealer record. If no URL,

Layer 2 is skipped entirely.

4. Web Scraper Worker — HTTP GET to target URL (homepage + contact/about page).

Enforces 5s timeout, robots.txt, MIME type guard, and read-only GET.

5. Field Extractor — Parses raw HTML and extracts dealership name, DBA, address, phones,

email, operating hours, and logo URL with confidence scores.

6. Field Comparator — Compares extracted values against contract values and classifies fields

as match, different, new, or missing.

7. Comparison View Renderer — Injects comparison map into the Dealer Details Review

screen.

8. Session Cache — Caches comparison result keyed by (dealership_id, session_id).

9. TAO Dealer Record Write — On Dealer Admin submit, confirmed final values are persisted.

URL Validation (for dealer-admin-provided alternate URLs)

10. URL Validator — Domain block-list check; scrape and fuzzy-match extracted business name

against contract dealership name. Below 0.70 rejects, 0.70–0.85 prompts, and >= 0.85

accepts silently.

Non-Functional Requirements

Screen load latency: Dealer Admin screen must render from Layer 1 data in < 500ms.

Layer 1 is blocking: Dealer Admin cannot open the Dealer Details Review screen until DWS-

SI-00 is complete.

Layer 2 is always additive: Any Layer 2 failure falls back silently to Layer 1 data only.

Rate limiting: Max 1 scrape per (dealership_id, session); max 1 user-triggered re-scrape per 5

minutes per dealership.

Security: Read-only HTTP GET only. No auth. No cookies. No form submissions.

§12. Technical Approach

Standard feature mode — engineering-review format. AI capability mapping

not required.

Architecture — Two-Layer Model

This feature has two independent layers that compose on the Dealer Details Review screen.

Layer 1 — Internal Data Sync (baseline, always runs)

Data flow:  Salesforce → TOC → TAO

1. TOC Sync Service — At IM provisioning stage, reads the dealer record from TOC. TAO does

not connect to Salesforce directly — TOC is the single API call.

2. TAO Dealer Record — Stores the TOC-sourced dealer record. Dealer Admin screen reads

from here. Always populated before the Dealer Admin journey begins.

Layer 2 — Website Scraping + Comparison (enrichment, additive)

3. Scrape Trigger — Resolves the dealer website URL from the TAO dealer record. If no URL,

Layer 2 is skipped entirely.

4. Web Scraper Worker — HTTP GET to target URL (homepage + contact/about page).

Enforces 5s timeout, robots.txt, MIME type guard, and read-only GET.

5. Field Extractor — Parses raw HTML and extracts dealership name, DBA, address, phones,

email, operating hours, and logo URL with confidence scores.

6. Field Comparator — Compares extracted values against contract values and classifies fields

as match, different, new, or missing.

7. Comparison View Renderer — Injects comparison map into the Dealer Details Review

screen.

8. Session Cache — Caches comparison result keyed by (dealership_id, session_id).

9. TAO Dealer Record Write — On Dealer Admin submit, confirmed final values are persisted.

URL Validation (for dealer-admin-provided alternate URLs)

10. URL Validator — Domain block-list check; scrape and fuzzy-match extracted business name

against contract dealership name. Below 0.70 rejects, 0.70–0.85 prompts, and >= 0.85

accepts silently.

Non-Functional Requirements

Screen load latency: Dealer Admin screen must render from Layer 1 data in < 500ms.

Layer 1 is blocking: Dealer Admin cannot open the Dealer Details Review screen until DWS-

SI-00 is complete.

Layer 2 is always additive: Any Layer 2 failure falls back silently to Layer 1 data only.

Rate limiting: Max 1 scrape per (dealership_id, session); max 1 user-triggered re-scrape per 5

minutes per dealership.

Security: Read-only HTTP GET only. No auth. No cookies. No form submissions.

§12. Technical Approach

Standard feature mode — engineering-review format. AI capability mapping

not required.

Architecture — Two-Layer Model

This feature has two independent layers that compose on the Dealer Details Review screen.

Layer 1 — Internal Data Sync (baseline, always runs)

Data flow:  Salesforce → TOC → TAO

1. TOC Sync Service — At IM provisioning stage, reads the dealer record from TOC. TAO does

not connect to Salesforce directly — TOC is the single API call.

2. TAO Dealer Record — Stores the TOC-sourced dealer record. Dealer Admin screen reads

from here. Always populated before the Dealer Admin journey begins.

Layer 2 — Website Scraping + Comparison (enrichment, additive)

3. Scrape Trigger — Resolves the dealer website URL from the TAO dealer record. If no URL,

Layer 2 is skipped entirely.

4. Web Scraper Worker — HTTP GET to target URL (homepage + contact/about page).

Enforces 5s timeout, robots.txt, MIME type guard, and read-only GET.

5. Field Extractor — Parses raw HTML and extracts dealership name, DBA, address, phones,

email, operating hours, and logo URL with confidence scores.

6. Field Comparator — Compares extracted values against contract values and classifies fields

as match, different, new, or missing.

7. Comparison View Renderer — Injects comparison map into the Dealer Details Review

screen.

8. Session Cache — Caches comparison result keyed by (dealership_id, session_id).

9. TAO Dealer Record Write — On Dealer Admin submit, confirmed final values are persisted.

URL Validation (for dealer-admin-provided alternate URLs)

10. URL Validator — Domain block-list check; scrape and fuzzy-match extracted business name

against contract dealership name. Below 0.70 rejects, 0.70–0.85 prompts, and >= 0.85

accepts silently.

Non-Functional Requirements

Screen load latency: Dealer Admin screen must render from Layer 1 data in < 500ms.

Layer 1 is blocking: Dealer Admin cannot open the Dealer Details Review screen until DWS-

SI-00 is complete.

Layer 2 is always additive: Any Layer 2 failure falls back silently to Layer 1 data only.

Rate limiting: Max 1 scrape per (dealership_id, session); max 1 user-triggered re-scrape per 5

minutes per dealership.

Security: Read-only HTTP GET only. No auth. No cookies. No form submissions.

§12. Technical Approach

Standard feature mode — engineering-review format. AI capability mapping

not required.

Architecture — Two-Layer Model

This feature has two independent layers that compose on the Dealer Details Review screen.

Layer 1 — Internal Data Sync (baseline, always runs)

Data flow:  Salesforce → TOC → TAO

1. TOC Sync Service — At IM provisioning stage, reads the dealer record from TOC. TAO does

not connect to Salesforce directly — TOC is the single API call.

2. TAO Dealer Record — Stores the TOC-sourced dealer record. Dealer Admin screen reads

from here. Always populated before the Dealer Admin journey begins.

Layer 2 — Website Scraping + Comparison (enrichment, additive)

3. Scrape Trigger — Resolves the dealer website URL from the TAO dealer record. If no URL,

Layer 2 is skipped entirely.

4. Web Scraper Worker — HTTP GET to target URL (homepage + contact/about page).

Enforces 5s timeout, robots.txt, MIME type guard, and read-only GET.

5. Field Extractor — Parses raw HTML and extracts dealership name, DBA, address, phones,

email, operating hours, and logo URL with confidence scores.

6. Field Comparator — Compares extracted values against contract values and classifies fields

as match, different, new, or missing.

7. Comparison View Renderer — Injects comparison map into the Dealer Details Review

screen.

8. Session Cache — Caches comparison result keyed by (dealership_id, session_id).

9. TAO Dealer Record Write — On Dealer Admin submit, confirmed final values are persisted.

URL Validation (for dealer-admin-provided alternate URLs)

10. URL Validator — Domain block-list check; scrape and fuzzy-match extracted business name

against contract dealership name. Below 0.70 rejects, 0.70–0.85 prompts, and >= 0.85

accepts silently.

Non-Functional Requirements

Screen load latency: Dealer Admin screen must render from Layer 1 data in < 500ms.

Layer 1 is blocking: Dealer Admin cannot open the Dealer Details Review screen until DWS-

SI-00 is complete.

Layer 2 is always additive: Any Layer 2 failure falls back silently to Layer 1 data only.

Rate limiting: Max 1 scrape per (dealership_id, session); max 1 user-triggered re-scrape per 5

minutes per dealership.

Security: Read-only HTTP GET only. No auth. No cookies. No form submissions.

2.3 Business Context

The Dealer Details Review screen must never be blank. When a dealer signs a contract with

Tekion, their basic details — name, address, phone, website URL — are captured in Salesforce.

Salesforce is already integrated with TOC (Tekion Operating Cloud) and syncs dealer data into

TOC as part of the contracting and provisioning pipeline. TAO connects to TOC only; TAO does

not read from Salesforce directly.

Data flow: Salesforce → TOC → TAO

Layer 1 — Internal data sync (baseline, always present): At provisioning stage, TAO reads

dealer details from TOC (which already holds the Salesforce-synced contract data plus any

provisioning-stage updates). When the Dealer Admin opens the Dealer Details Review screen,

all fields are already populated. There is no TAO-side merge step — TOC owns the

reconciliation.

Layer 2 — Website scraping (enrichment, additive): For dealers with a public website, TAO

scrapes it and compares what it finds against the on-file record. The website scrape surfaces

differences without discarding what Tekion already knows.

The Dealer Admin experience: When the Dealer Admin opens the screen they see:

All fields pre-populated from TOC record, labelled "From your records on file"

Where the website found something different or new: "On file: 123 Main St | Found on

website: 123 Main Street, Suite 100 | Use website version?"

Where the website found the same value → a quiet checkmark

Where the website found nothing → on-file value shown alone

Small dealers with no website: TOC/contract data fills the screen completely. No comparison

rows. This is the ideal baseline — not a degraded experience.

§12. Technical Approach

Architecture — Two-Layer Model

Data flow:  Salesforce → TOC → TAO

Layer 1 — Internal Data Sync (baseline, always runs)

1. TOC Sync Service — At IM provisioning stage, reads the dealer record from TOC. TOC

already holds the Salesforce-synced contract data (legal name, address, phone, website URL)

plus any provisioning-stage updates. TAO does not connect to Salesforce directly.

2. TAO Dealer Record — Stores the TOC-sourced dealer record. Dealer Admin screen reads

from here. Always populated before the Dealer Admin journey begins. This is a blocking

dependency for the Dealer Admin screen load.

Layer 2 — Website Scraping + Comparison (enrichment, additive)

3. Scrape Trigger — Resolves dealer website URL from TAO dealer record. If no URL → Layer 2

skipped entirely; Layer 1 data shown alone.

4. Web Scraper Worker — HTTP GET to target URL. Enforces: 5s timeout, robots.txt check,

MIME type guard (HTML only), read-only GET only. On failure → Layer 1 shown alone; no

error to Dealer Admin.

5. Field Extractor — Parses raw HTML; extracts dealership name, address, phone, website URL.

Assigns confidence score (0.0–1.0) per field. Fields below 0.80 suppressed.

6. Field Comparator — Classifies each field as: match / different / new / missing. Returns

structured comparison map.

7. Comparison View Renderer — Injects comparison map into screen. TOC values always

shown as baseline. Diff/new rows shown for Dealer Admin decision. Match fields show quiet

checkmark.

8. Session Cache — Caches comparison result by (dealership_id, session_id). IM pre-scrape

result reused on Dealer Admin screen load if not stale.

9. TAO Dealer Record Write — On Dealer Admin submit, confirmed values (TOC baseline + any

website values accepted) persisted via existing dealer details save endpoint.

URL Validation (Dealer Admin-provided alternate URLs)

10. URL Validator — Domain block-list check (immediate). If passes → scrape → business name

fuzzy-match against contract name. < 0.70 → reject. 0.70–0.85 → confirmation prompt. >=

0.85 → accept silently.

Non-Functional Requirements

Screen load latency: Dealer Admin screen must render from Layer 1 data in < 500ms. Layer 2

runs asynchronously; never blocks the screen.

Layer 1 is blocking: Dealer Admin cannot open the screen until TOC sync (DWS-SI-00) is

complete.

Layer 2 is always additive: Any Layer 2 failure falls back silently to Layer 1 data. No Dealer

Admin-visible error.

Rate limiting: Max 1 scrape per (dealership_id, session). Max 1 user-triggered re-scrape per 5

minutes.

Security: Read-only HTTP GET only. No auth. No cookies. No form submissions.
